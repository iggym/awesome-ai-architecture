Agent Security & Sandboxing

Watchtower and Moat

Why LLM-layer guards and runtime sandboxes solve different failure modes — and why stacking both is the only architecture that survives adversarial pressure.

Stack Maturity Spectrum
Single-layer: just a content filter or just a container 1L
Layered defense: LLM-layer guards + runtime execution boundary 2L

The Real Problem

Every curated list of agent security tools makes the same mistake: it presents a flat inventory of products as if they solve the same problem. They don't. Agent security has two fundamentally different failure modes — what the model says and what the agent does — and conflating them leads to architectures that are secure against neither.

The standard "awesome list" gives you Guardrails AI next to E2B next to Llama Guard as if they're interchangeable entries in a dropdown. An architecture leader evaluating these tools needs to understand that picking any single one of them leaves a failure mode wide open. This guide maps five real tools to the two distinct security layers they actually serve, with the explicit trade-offs that determine which one you need — and why you likely need both.

What Got Cut

Five categories were deliberately excluded. General-purpose API security tools (Cloudflare AI Gateway, etc.) lack agent-specific execution semantics. Red-teaming frameworks (HarmBench, JailbreakBench) are evaluation instruments, not production defenses. Prompt observability platforms (Langfuse, PromptLayer) watch but don't block. Enterprise DLP tools retrofitted for AI weren't architecturally designed for LLM attack surfaces. And safety-tuned model variants embed defense at training time — useful, but not a runtime control. If your architecture depends solely on a model's fine-tuning to prevent harm, you have no runtime defense when the fine-tuning fails.

The Two Layers

LLM-Layer Security operates at the boundary between the model and the world. It inspects what goes in and what comes out. Three tools occupy this layer, each with a distinct granularity trade-off.

Prompt Guard

Prompt Guard (Meta) is the fastest, narrowest tool. A ~300M parameter encoder that runs on CPU in under 10ms. It answers exactly one question: "Is this input an injection attempt?" Binary classification, no nuance, no correction. Use it as a first-line filter before anything else reaches your model. Its limitation is its specificity — it won't catch a model producing harmful content from a benign prompt, because it doesn't look at outputs.

Llama Guard 2

Llama Guard 2 (Meta) is the broadest LLM-layer tool. An 8B parameter model that classifies both inputs and outputs against a full safety taxonomy. It catches what Prompt Guard can't — harmful content the model generates from legitimate prompts. The trade-off is infrastructure: you need a dedicated GPU, 100-300ms of latency per classification, and the taxonomy is fixed unless you re-prompt the guard model itself. This is your watchtower — high vantage point, wide view, expensive to operate.

Guardrails AI

Guardrails AI sits between the two extremes. Middleware that intercepts LLM I/O and applies composable validators — JSON schema enforcement, PII redaction, custom Python logic. It can both detect and correct outputs, which neither Meta tool does. The trade-off is compositional complexity: as your rule set grows, validator interaction bugs become a real maintenance burden, and each validator adds 50-200ms.

Runtime Execution Boundary is architecturally distinct. These tools don't care what the model says — they constrain what the agent can do.

E2B

E2B provides isolated microVM sandboxes via Firecracker. Each agent gets a dedicated kernel, isolated filesystem, and configurable network egress. The architecture is clean: your agent code runs inside the sandbox, and the sandbox policy is the security boundary. Cold start is ~500ms on managed infra. The limitation is granularity — E2B controls filesystem and network, but not individual function calls or in-process memory access. If an agent needs to call a specific API, you allow network egress to that domain, and the agent can do anything on that domain.

Archon

Archon (OpenAI) takes a different approach: capability-based security. Agents declare what they want to do (read a file, make a network request, execute a shell command), and a supervisor process approves or denies each capability invocation based on declarative policy. This is finer-grained than E2B's network/filesystem boundaries — you can allow "read file X" but not "read file Y," or "call API endpoint A" but not "call API endpoint B." The trade-off is that the policy language is still young, the process isolation adds overhead, and it's currently Python-only. But architecturally, it's the most precise execution boundary available.

Where to Land

The decision matrix is simple once you separate the layers. If your agent only generates text — no tool use, no code execution, no side effects — LLM-layer security alone is sufficient. Pair Prompt Guard (fast, narrow) with Guardrails AI (corrective) and you have a solid I/O pipeline.

If your agent takes actions — writes files, calls APIs, executes code — you need a runtime boundary. Period. E2B for coarse-grained isolation (fastest to deploy), Archon for fine-grained capability control (most precise, higher operational cost). Stack either with LLM-layer guards above.

The failure mode of choosing only one layer is asymmetric and dangerous. LLM-layer guards alone cannot stop an agent that's been instructed to exfiltrate data through allowed channels — the guard sees a legitimate API call, the model output is clean, but the agent ships your secrets to an external endpoint. Runtime sandboxes alone cannot stop an agent from producing harmful content that reaches the user before execution is halted — the sandbox contains the action, not the utterance.

Watchtower and moat. Neither replaces the other. The architecture that stacks both is the one that survives the first real adversarial test.

One Move

Map your agent's data flow from user input to side effect. Identify every point where text crosses a boundary (LLM-layer) and every point where an action crosses a boundary (runtime). If you have a gap in either layer, you have a vulnerability. Close it this sprint.
