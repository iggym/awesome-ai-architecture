Where Agents Break Free

Agent security's blind spot — and the five tools that actually matter

Legacy Stack Modern Stack
LLM guard only Full defense-in-depth
A prompt guardrail cannot stop an agent from opening a network socket.

The Real Threat

Every CTO running agents in production shares one nightmare scenario: an LLM generates a rm -rf / wrapped in plausible-looking code, and your infrastructure either catches it or doesn't. The problem isn't that teams ignore security—it's that they systematically secure the wrong layer. Based on patterns observed across teams shipping agents at scale, the vast majority of security investment flows into prompt guardrails and output filtering—what we'll call LLM-layer security. Meanwhile, the runtime where agents actually execute code—the shell, the filesystem, the network socket—gets a docker run --rm and a prayer.

Standard "awesome" lists compound this failure by lumping prompt-injection defenses next to sandbox runtimes as if they solve the same problem. They don't. A prompt guardrail cannot stop an agent from opening a network socket to exfiltrate data. A sandbox cannot detect that an agent's tool response contains subtly encoded instructions designed to manipulate a downstream human reviewer. These are fundamentally different threat classes requiring fundamentally different architectures, and treating them as interchangeable is the most expensive mistake in the current agent stack.

This guide maps five tools across two architectural camps so you can identify gaps in your stack with precision rather than guesswork.

What We Cut

Deliberately excluded: general-purpose container security tools not evaluated in agent contexts (Falco, Aqua Security), prompt-injection detection frameworks without runtime integration (Promptfoo's injection tests used in isolation), and supply-chain security tools (Sigstore, SLSA frameworks). Also excluded: proprietary platform sandboxes that don't expose architectural details (OpenAI Code Interpreter's internal sandbox). If we can't evaluate the architectural trade-off, it doesn't belong here.

The Two Camps

Agent security splits into two fundamentally different architectures. Conflating them is the single most expensive mistake in current stack design.

Runtime Boundaries

These tools enforce isolation at the execution layer—where the agent's generated code actually runs. They answer the question: if the LLM produces malicious code, what can it reach?

E2B

github.com/e2b-dev/e2b · Firecracker microVM per session

Strengths: Purpose-built for agents—per-session isolation maps directly to conversation boundaries, language-agnostic SDK (Python, JS, Go), open-core with self-host path, 150ms cold start.

Trade-offs: Self-hosted mode demands Kubernetes plus Firecracker infrastructure; cloud-hosted introduces per-session cost and network latency; no built-in structured audit logging beyond stdout capture.

Exclude if: your agents need GPU access inside sandboxes.

gVisor

github.com/google/gvisor · Application kernel syscall interception

Strengths: Drops into existing Kubernetes with zero code changes, ~70% kernel attack surface reduction, GPU support via NVIDIA Container Toolkit, CNCF graduated with years of production hardening at Google scale.

Trade-offs: 5–15% performance overhead on syscall-heavy workloads, no agent-aware features (no per-conversation isolation, no LLM response auditing), requires Kubernetes context to deliver value.

Exclude if: your team lacks container orchestration infrastructure.

Wasmtime

github.com/bytecodealliance/wasmtime · Capability-based Wasm sandbox

Strengths: Minimal attack surface with no Linux kernel exposure, sub-millisecond instantiation, deterministic execution enables full replay-based auditing, language-agnostic compilation target.

Trade-offs: Near-zero AI/ML ecosystem support in Wasm—no PyTorch, no NumPy without significant porting effort, fundamentally unsuitable for agents invoking the Python data science stack.

Exclude if: your agents rely on any non-trivial Python package ecosystem.

LLM-Layer Shields

These tools operate on the LLM's input and output streams—filtering, classifying, and validating before and after inference. They answer the question: should this prompt be sent, and is this response safe?

Llama Guard 2

huggingface.co/meta-llama/Llama-Guard-2-8B · 8B-param safety classifier

Strengths: Open-weights with permissive license, fine-tunable for custom policies, catches semantic risks pattern-matching cannot (e.g., "write a script that slowly degrades system performance" passes regex but fails intent classification).

Trade-offs: Adds a full 8B-parameter inference pass per request—roughly doubles latency and compute cost, categorical taxonomy may miss domain-specific threats without fine-tuning, bypassable via obfuscated multi-turn instructions.

Exclude if: your agent operates in latency-sensitive real-time loops where doubling request time is unacceptable.

Guardrails AI

github.com/guardrails-ai/guardrails · Structured output validation

Strengths: Ensures structural correctness of tool calls—malformed JSON is a top agent failure mode, composable validator chains, streaming validation support for long outputs.

Trade-offs: Cannot detect semantic risks—validates form, not intent; adds pipeline complexity with its own failure modes; misconfigured validators silently reject valid outputs or accept dangerous ones.

Exclude if: evaluating as a standalone security solution—must be paired with runtime isolation.

Pick Your Wall

The decision isn't runtime or LLM-layer—it's which you deploy first, because sequencing matters.

Runtime boundaries are load-bearing walls. LLM-layer shields are insulation. Both are necessary, but you frame walls before you insulate. Most teams do the opposite.

Recommendation: If you run code-executing agents in production with only LLM-layer guards, add E2B or gVisor this quarter. If you have neither, start with gVisor (assuming Kubernetes) or E2B (if cloud-native), then layer Llama Guard 2 and Guardrails AI the following quarter.

One Move Now

Audit one agent in production: trace a single tool-call path from LLM output to code execution and name every security boundary it crosses. If the count is zero runtime boundaries, you have your next quarter's priority.
