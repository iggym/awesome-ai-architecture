Vector & Hybrid Retrieval Stores, Mapped by Failure Mode

For engineers choosing the retrieval layer under a RAG system or agent — organized by the way retrieval actually fails in production, not by who tops this month's ANN benchmark.

  • retrieval
  • vector-database
  • hybrid-search
  • rag

Exclusion Criteria — Read First

Every RAG tutorial ships with a vector store, and most "best vector database" lists are a leaderboard of synthetic recall numbers. This one is not.

  • In-memory libraries presented as databases. FAISS, hnswlib and Annoy are excellent index libraries, but they have no durability, no filtering model and no concurrent writes. If you have to build the database around it, it is a component, not a store.
  • Embedded toy stores in framework quick-starts. a vector store that exists to make a notebook run is not evidence of production behaviour under filters, updates and tenancy.
  • Closed SaaS with no published architecture. if the vendor cannot tell you how filtering, consistency and index rebuilds work, you cannot reason about its failure modes — and failure modes are the whole point of this list.
  • Benchmark-only claims. an ANN-Benchmarks win on unfiltered, static data says nothing about recall with a tenant filter on a corpus that changes every hour.

Inclusion bar: the store must persist data, support filtered queries and live updates, and document how it behaves when all three happen at once.

Recall Collapses the Moment You Add a Filter

Real queries are never just "nearest neighbours" — they are nearest neighbours for this tenant, this product line, documents newer than March. Post-filtering an approximate index silently returns three results when you asked for ten, and pre-filtering can force a brute-force scan. Your offline eval, run without filters, never notices.

Filtered Recall

Qdrant

Builds filter awareness into the HNSW graph via payload indexes, so selective filters stay on the fast path instead of degrading to a scan; fits multi-tenant and heavily-filtered RAG where every query carries metadata predicates, not single-corpus semantic search.

Limit: you must declare payload indexes for the fields you filter on — forget one and you are back to slow paths.

Dense Embeddings Miss the Exact Token That Mattered

Error codes, SKUs, function names, legal clause numbers: dense embeddings smear them into "something similar". A user who searches ERR_4471 gets documents about errors in general. Hybrid retrieval — lexical BM25 fused with dense vectors — is the fix, but only if fusion and score normalisation are first-class, not a second system you glue on.

Lexical Misses

Weaviate

Runs BM25F and vector search in one query with configurable fusion and an alpha weight; fits teams that want hybrid search as a single API call rather than two systems and a merge function.

Limit: tuning alpha per query type is on you; one global weight rarely suits both keyword-heavy and conceptual queries.

Lexical Misses

Vespa

Expresses retrieval and multi-phase ranking (lexical, dense, learned rankers) as declarative rank profiles executed next to the data; fits search-heavy products that need ranking control beyond fusion, not teams that want a managed index in an afternoon.

Limit: the schema and rank-profile model is a real learning curve.

Lexical Misses

OpenSearch

Adds k-NN fields and hybrid queries with score-normalisation processors to an engine many platform teams already operate; fits organisations whose logs and site search already run on OpenSearch and who want one cluster to own, not another datastore.

Limit: vector performance depends heavily on engine and index settings; defaults are tuned for text search, not ANN.

The Vector Store Drifts Out of Sync with the System of Record

A second datastore means a second copy of the truth. Deletes that never propagate, permission changes that lag, documents re-indexed out of order — the RAG system confidently cites a policy that was revoked last Tuesday. The cheapest consistency model is not having two databases.

Store Drift

pgvector

Vector columns and HNSW/IVFFlat indexes inside Postgres, so embeddings commit in the same transaction as the row and its permissions; fits teams whose source data already lives in Postgres and whose corpus is in the millions, not billions.

Limit: filtered ANN and very large indexes need careful tuning (iterative scans, partitioning); it is a Postgres extension, not a dedicated engine.

Memory Bills Explode Before Recall Does

HNSW wants the graph in RAM. At hundreds of millions of vectors — or millions of small tenant namespaces — the index costs more than the models querying it. The failure is not a crash; it is a quarterly review where retrieval is the biggest line item and nobody can explain why idle tenants cost money.

Cost at Scale

Milvus

Distributed engine with disk-based (DiskANN) and quantised indexes and separated storage/compute; fits billion-scale single collections where you need to trade RAM for SSD deliberately, not small corpora that fit on one node.

Limit: the distributed deployment has many moving parts; the operational surface is the price of the scale.

Cost at Scale

turbopuffer

Object-storage-first search (vectors plus BM25 full-text) with NVMe/memory caching for hot namespaces, so cold tenants cost storage prices rather than RAM prices; fits SaaS products with many tenants and skewed access, not latency-critical workloads that are uniformly hot.

Limit: cold queries pay an object-storage round trip; it is a managed service, not self-hostable open source.

Changing the Embedding Model Means a Risky Big-Bang Migration

Embedding models improve every few months. Switching means re-embedding the whole corpus, running old and new indexes side by side, comparing retrieval quality and cutting over without downtime. Stores that treat the index as immutable turn every model upgrade into a weekend migration — so teams stop upgrading.

Re-embedding

LanceDB

Built on the Lance columnar format with table versioning and cheap column additions, so a new embedding column can be backfilled next to the old one and compared before cutover; fits teams that iterate on embedding models and want retrieval data to behave like versioned tables, not a black-box index.

Limit: the multi-node, high-QPS story is younger than the dedicated servers above; check the deployment mode you need.

How to Choose

Start with the data you already have. If the documents and their permissions live in Postgres and the corpus is in the low millions, pgvector removes an entire class of sync bugs, and that is worth more than any recall delta you will measure. Move to a dedicated store when you can name the failure that forces you to — not when a benchmark tells you to.

Then write down your real query shape before comparing engines. What fraction of queries carry a filter, and how selective is it? How many contain identifiers that must match exactly? How many tenants are there, and what share are active in a given hour? Those three numbers point to Qdrant, a hybrid engine or an object-storage design far more reliably than a recall chart does.

Finally, decide how you will change embedding models before you need to. Whatever store you choose, keep the raw text and metadata outside the index, version the embedding model name next to every vector, and rehearse a side-by-side re-embed on a sample. A store you cannot migrate off is a decision you make once and pay for every quarter.

Bold Reframe

Vector databases don't fail on recall benchmarks — they fail on the filter, the SKU and the re-embed. Choose the store by the failure you can't afford.

What's Still Missing (as of Oct 2026)

Nobody ships a good answer for evaluating retrieval under production filters — recall is still measured on unfiltered benchmark sets while real traffic is almost entirely filtered. Permission-aware retrieval (document ACLs that change hourly) remains an exercise left to the application, and there is no portable format for moving an index plus its metadata between stores. Until those exist, the safest retrieval architecture is the one with the fewest copies of your data.
