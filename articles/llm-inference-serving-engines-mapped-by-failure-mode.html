LLM Inference & Serving Engines, Mapped by Failure Mode

For platform and ML engineers running open-weight models on their own hardware — organized by how serving actually fails under real traffic, not by tokens-per-second on a single prompt.

Exclusion Criteria — Read First

Serving is the layer where benchmarks lie most. A single-request throughput chart tells you nothing about batching, cache reuse or the tail.

  • Engines in maintenance mode. Hugging Face's Text Generation Inference entered maintenance mode in December 2025 and itself recommends vLLM or SGLang. An existing TGI deployment need not be ripped out, but it is not a default for new systems.
  • Hosted inference APIs. managed endpoints solve a procurement problem, not a serving-architecture one; they belong in the gateway and routing reference, not here.
  • Research prototypes without a server. a kernel or scheduling paper with a demo script is not something you can put behind a load balancer. If it matters, it usually lands inside vLLM or SGLang within a release or two.
  • Generic model servers with no LLM-specific scheduling. a server that runs one request per forward pass, with no continuous batching or KV-cache management, wastes most of the GPU on autoregressive workloads.

Inclusion bar: an OpenAI-compatible (or equivalent) server, continuous batching or an explicit reason it is unnecessary, and a release inside the research window.

Throughput Collapses Under Concurrency

The demo serves one user beautifully. At fifty concurrent requests, naive serving pads batches to the longest sequence, fragments KV-cache memory and leaves the GPU idle between tokens. Cost per token climbs exactly when usage succeeds.

Throughput Collapse

vLLM

PagedAttention for KV-cache memory, continuous batching, automatic prefix caching and the broadest model and hardware coverage of any open engine; fits teams that want one default engine across many models and accelerators, not teams chasing the last few percent on a single fixed model.

Limit: fast-moving releases mean configuration flags and defaults change often — pin versions and re-benchmark on upgrade.

Agents Recompute the Same Prefix on Every Turn

Agent and multi-turn workloads resend a long system prompt, tool schema and conversation history on every call. Without cache reuse across requests, the engine re-runs prefill on thousands of identical tokens per turn — the most expensive tokens are the ones it already saw.

Prefix Recompute

SGLang

RadixAttention keeps a radix tree of KV caches so shared prefixes are reused across requests automatically, with a frontend language for structured multi-call programs; fits agentic, multi-turn and tree-of-calls workloads with heavy prefix overlap, not one-shot batch jobs with unique prompts.

Limit: the biggest wins depend on prefix overlap in your real traffic — measure the cache hit rate before crediting the engine.

Prefill Bursts Wreck Tail Latency at Scale

One long-context prefill stalls every decode stream sharing that GPU. Round-robin load balancing then sends the next request to a replica that has none of its prefix cached. At cluster scale, p99 latency is a scheduling problem — routing, disaggregation and cache placement — not a kernel problem.

Tail Latency

NVIDIA Dynamo

Datacenter-scale serving layer that disaggregates prefill and decode onto separate workers, moves KV cache between them with NIXL and routes requests by KV-cache overlap; fits multi-node GPU fleets serving large models where tail latency is the SLO, not a single-GPU deployment.

Limit: it orchestrates engines (vLLM, SGLang, TensorRT-LLM) rather than replacing them, so you operate both layers.

Tail Latency

llm-d

Kubernetes-native distributed inference with inference-aware routing, prefill/decode disaggregation and hierarchical KV offload, built on vLLM; a CNCF Sandbox project since March 2026. Fits platform teams who want inference scheduling to be Kubernetes primitives, not a separate control plane.

Limit: young project (v0.x) — expect APIs and Helm values to move.

Leaving Performance on Expensive Hardware

When the model is fixed and the fleet is large, every percent of throughput is real money. General-purpose engines trade peak performance for flexibility; at enough scale that trade inverts.

Hardware Waste

TensorRT-LLM

NVIDIA's optimised runtime with fused kernels, FP8/FP4 quantisation paths and in-flight batching for NVIDIA GPUs; fits large, stable deployments of a few models on NVIDIA hardware where peak efficiency justifies extra build complexity, not heterogeneous fleets or fast model churn.

Limit: NVIDIA-only, and new model architectures can land later than in vLLM or SGLang.

There Is No Datacenter GPU Where the Model Has to Run

Air-gapped sites, laptops, on-device assistants and cost-sensitive internal tools often have CPUs, Apple silicon or one consumer GPU. Datacenter engines assume CUDA and gigabytes of headroom; here the failure is that the model does not run at all.

No Datacenter GPU

llama.cpp

C/C++ inference with GGUF quantisation across CPU, Metal, CUDA, Vulkan and more, plus a built-in OpenAI-compatible server; fits edge, offline and developer-machine deployments where portability beats throughput, not high-concurrency serving.

Limit: concurrency and batching are modest compared with datacenter engines.

No Datacenter GPU

Ollama

Packages local models with one-command pulls, a model registry and a local API; fits developer workstations and small internal tools that need a model running in minutes, not production multi-tenant serving.

Limit: convenience defaults (context size, quantisation) hide choices you will eventually need to make explicitly.

How to Choose

Default to vLLM or SGLang for a new deployment and let measurements move you off it. Run both on a replay of your own traffic — real prompt lengths, real concurrency, real prefix overlap — and compare time-to-first-token and inter-token latency at p50 and p99, not peak throughput. The engine that wins on a single long prompt often loses on fifty short agent turns.

Add a cluster layer such as Dynamo or llm-d only when a single replica's tail latency, or cache misses caused by naive load balancing, is the measured bottleneck. Disaggregation is real engineering with real operational cost; it pays off on large models and large fleets, and rarely before. TensorRT-LLM earns its build complexity when the model is stable and the GPU bill is large enough that ten percent matters.

Keep the serving API OpenAI-compatible at the boundary, whichever engine is behind it. That one decision lets your gateway, evals and cost tooling stay unchanged when you switch engines — and in this layer you will switch engines, because the leader changes every few releases.

Bold Reframe

Inference engines aren't ranked by peak tokens per second — they're ranked by what happens at p99 when the 500th concurrent agent sends the same 8k-token prefix.

What's Still Missing (as of Oct 2026)

There is still no neutral, reproducible benchmark for realistic serving: mixed context lengths, prefix overlap, bursty arrivals and an SLO on p99 time-to-first-token. Every vendor publishes its own harness. KV-cache portability across engines is also unsolved — a cache built by one engine cannot be served by another, which keeps disaggregated and tiered caching locked to a single stack. Until those exist, run your own traffic replay before believing anyone's chart.
