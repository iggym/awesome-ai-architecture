The Plug Is Not the Policy

MCP solved the integration problem so well that teams forgot it was never meant to solve the trust problem. A standard plug makes it easier to connect anything — including the wrong thing.

LegacyBespoke tool integrations per agent; credentials pasted into config; trust implied by "it's on the list".
ModernStandard protocol plus audience-bound auth, scanned and pinned servers, a gateway that enforces policy, and a separate contract for agent-to-agent work.

The Real Problem

Before the Model Context Protocol, connecting an agent to a tool meant custom glue for every pair. MCP replaced that with one client-server contract, and adoption followed: Anthropic donated the protocol to the Linux Foundation's new Agentic AI Foundation in December 2025, and most major AI clients now speak it. That success is the problem this essay is about.

A tool server is code that runs with your credentials and whose descriptions are read by your model as instructions. A poisoned tool description is a prompt injection with a persistent foothold. A server that silently changes its tool definitions after you approved it is a rug pull. A token that a server forwards upstream is a confused deputy. None of these is a flaw in the plug; they are the absence of a policy around it.

The scale makes it urgent. When a protocol is easy enough that any developer can connect a new server in a minute, the number of connected servers grows faster than any review process. The registry now lists thousands of public servers, and most organisations cannot say how many are running on their own developers' machines, which credentials those servers hold, or whether their tool descriptions changed since the day they were installed.

The protocol is the easy decision. The architecture is the four layers you put around it.

What Got Cut

  • Directory sites that list servers. a catalogue of thousands of servers with no publisher verification is a discovery convenience, not a control.
  • Individual MCP servers. the GitHub, Slack or database server you install is the thing being governed, not part of the governance.
  • Agent frameworks' tool abstractions. framework-specific tool decorators matter, but they are covered by the agent-orchestration essays on this site.
  • Generic API gateways without MCP awareness. they can rate-limit HTTP, but they cannot see a tool call, a tool description or a session — so they cannot enforce a tool policy.

Inclusion bar: the tool must enforce or verify something about the tool boundary — identity, authorization, provenance, isolation or the contract itself — not just make connection easier.

Four Layers Around the Plug

Read the layers from the inside out: the contract itself, who is allowed to call what, where tool servers come from, and what happens when the counterpart is another agent rather than a tool.

Contract & Authorization

The protocol is also where authorization starts. The current specification makes a protected MCP server an OAuth 2.1 resource server, and that design choice matters more than any feature list.

Contract & Authorization

MCP specification & SDKs · Agentic AI Foundation / Linux Foundation

The 2025-11-25 authorization spec requires PKCE, RFC 8707 resource indicators naming the target server, and audience validation on the server side, with protected-resource metadata (RFC 9728) for discovery. The practical rule is in one line: servers must not pass a client's token through to upstream APIs. Official SDKs implement the flows so you do not hand-roll them.

Limit: the spec defines what a correct server does; it cannot make the servers you install correct. Audit for token passthrough explicitly.

Supply Chain & Provenance

Tool servers are dependencies. They need the same three things as packages: a known publisher, a scan before install and a pin so they cannot change underneath you.

Supply Chain & Provenance

MCP Registry · MCP project

The official, open metadata registry for publicly available servers, with namespace verification tied to the publisher's domain or GitHub identity, designed so organisations can run sub-registries that mirror and curate it. Fits teams that want a single source of truth for which servers exist and who published them.

Limit: still in preview (REST API frozen at v0.1 since October 2025) — it records provenance; it does not vouch for safety.

Supply Chain & Provenance

Snyk Agent Scan · Snyk (formerly Invariant Labs' mcp-scan)

Discovers MCP servers and agent skills configured across local AI clients and scans them for tool poisoning, prompt injection in tool descriptions and toxic flows, with tool pinning that hashes definitions to catch rug pulls. Fits security teams that need an inventory of what developers have actually connected, not what policy says they connected.

Limit: scanning is detection at a point in time; pair it with a gateway that enforces the result.

Runtime Enforcement

Once a server is approved, something has to sit between the agent and the server at runtime: isolating the process, holding the secrets and deciding which tool calls go through.

Runtime Enforcement

Docker MCP Gateway · Docker

An open-source gateway that exposes many MCP servers to clients through a single endpoint, runs each server in its own container, injects credentials from a secrets store rather than environment variables, and applies interceptors and restrictions to calls. Fits teams standardising developer and agent access to tools on Docker or Kubernetes.

Limit: container isolation limits what a server can touch on the host; it does not stop a server from misusing the API scopes you granted it. Scope the tokens, too.

Agent-to-Agent Contracts

When the counterpart is another agent — with its own planning, long-running tasks and state — a tool contract is the wrong shape. Treating a remote agent as "just another tool" hides its failure modes.

Agent-to-Agent Contracts

A2A Protocol · Linux Foundation

An open protocol for agents to discover each other through agent cards, delegate work as tasks with an explicit state machine, and stream results over JSON-RPC, gRPC or REST. Version 1.0 (March 2026) added signed agent cards for identity, version negotiation and multi-tenancy. Fits cross-team or cross-vendor agent delegation where tasks outlive a single request.

Limit: most teams do not need it yet; if every "agent" you call is really a deterministic function, MCP is the simpler contract.

Where to Land

Adopt MCP as the contract — the ecosystem has decided. Then decide the policy deliberately, layer by layer, before the number of connected servers decides it for you.

The most common gap is not exotic: it is a developer laptop with a dozen servers nobody inventoried, holding long-lived personal tokens. Start there.

Treat tool servers the way mature teams treat open-source packages: an allow-list with owners, automated scanning, pinned versions and a rule that anything touching production data goes through the same gateway with logging. None of that is MCP-specific, which is exactly the point — the plug is new, but the policy is supply-chain hygiene you already know how to run.

Finally, keep the agent-to-agent question separate. When a remote counterpart plans, holds state and runs for minutes or hours, it needs a task contract and an identity of its own, not a tool schema.

  • You are building or exposing an MCP server → implement the 2025-11-25 authorization flow with audience-bound tokens, and never forward client tokens upstream.
  • Developers install servers themselves → inventory and scan them (Snyk Agent Scan), pin tool definitions, and publish an allow-list sourced from the MCP Registry or an internal sub-registry.
  • Agents call tools in shared or production environments → route through a gateway (Docker MCP Gateway or equivalent) that isolates servers, holds secrets and logs every tool call.
  • You delegate long-running work to another team's or vendor's agent → use A2A tasks with signed agent cards rather than wrapping the agent as a tool.
  • You have one agent and two internal tools → keep it simple: official SDK, scoped tokens, no gateway yet — but write the allow-list down.

One Move

Run an agent scanner on five developer machines this week and list every MCP server it finds, who published it and which credentials it holds. Anything without a known publisher or with a broader token than its job needs comes off the list. That inventory is your first policy.

What's Still Missing (as of Oct 2026)

There is no standard for tool-level authorization: OAuth scopes describe APIs, not "this agent may call create_issue but not delete_repo", so every gateway invents its own policy language. Tool descriptions are still unsigned text read by the model, which keeps tool poisoning a detection problem rather than a verification one. And audit trails do not travel — a tool call that crosses a gateway, a server and an A2A hop leaves three logs in three formats. Expect the next year of this layer to be about policy and provenance, not more connectors.
