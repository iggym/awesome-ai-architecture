Trust Is Not Armor

Standard lists of "AI security tools" commit a category error: they stack LLM guardrails alongside runtime sandboxes as if they solve the same problem. They don't.

Consider a concrete failure: an agent receives a prompt that passes all LLM-layer guardrails — no known jailbreak patterns, on-topic, syntactically benign output. But the LLM generates a tool call that, while valid in structure, instructs the execution environment to exfiltrate data to an external endpoint. The LLM-layer guardrail sees a legitimate API call. The sandbox, if it exists, sees a legitimate network request. Neither layer catches the semantic violation because that intent is distributed across the boundary.

An LLM-layer guardrail prevents a model from generating a harmful instruction. A sandbox prevents that instruction from executing with real consequences. These are orthogonal defenses protecting different boundaries, and treating them as interchangeable leaves a gap exactly where attackers operate — in the space between what the LLM says and what the runtime does. Architecture leaders need to think in terms of two distinct enforcement layers with a deliberately managed gap between them, not a single "security" checkbox.

What We Cut

  • General-purpose vulnerability scanners (Snyk, SonarQube): Static analysis for traditional code, not agent execution boundaries.
  • Prompt injection benchmark datasets (HarmBench, IFEval): Research artifacts, not deployable defenses.
  • Network-level security (mTLS, VPNs, zero-trust networks): Necessary infrastructure but orthogonal to the LLM-to-runtime execution boundary.
  • Container orchestration platforms (Kubernetes, Nomad) without agent-specific isolation policies: Security properties depend entirely on configuration, not what the platform provides by default.

Two Walls, One Gap

LLM-Layer Security: Stopping Harmful Intent at Generation

NeMo Guardrails
github.com/NVIDIA/NeMo-Guardrails
Architectural Pattern
Colang-based dialogue flow controllers intercepting LLM inputs and outputs against programmable rails, implemented as middleware between application and LLM API.
Strengths
Declarative rail definitions let non-security engineers encode policies. Supports topical, safety, and factual consistency rails. Integrates with LangChain and LlamaIndex. Apache 2.0 open-source.
Production Trade-offs
Adds 50–200ms latency per turn. Rail definitions grow brittle as agent capabilities expand — every new tool requires explicit rail coverage. Doesn't enforce anything at the execution layer; a prompt that bypasses rails but issues a valid tool call executes unimpeded.
Lakera Guard
lakera.ai
Architectural Pattern
API-first prompt injection and content filtering service classifying inputs across injection, jailbreak, and hallucination dimensions using ensemble detection models.
Strengths
Near-zero integration friction — drop-in API call. Continuous model updates without customer retraining. Low latency (30–80ms typical). Strong detection on published jailbreak benchmarks.
Production Trade-offs
Black-box detection; cannot inspect or modify classification logic. Cost scales linearly with request volume. Operates entirely at the LLM layer — a bypassed filter has no downstream enforcement mechanism.

Runtime Execution Boundary: Controlling What Actually Happens

E2B
e2b.dev / github.com/e2b-dev
Architectural Pattern
Per-request Firecracker microVMs provisioned via API. Each agent action requiring code execution, file system access, or network calls receives an isolated VM with a time-boxed lifecycle (default 300s).
Strengths
Strongest isolation in this landscape — full VM boundary with its own kernel. Ephemeral and stateless by design, preventing persistence attacks. Python/JS SDK with template-based environments. Adopted as execution backend by multiple agent frameworks.
Production Trade-offs
Cold start of 500ms–2s per sandbox, partially mitigated by warm pooling. Non-trivial cost at scale. Network egress requires explicit configuration. Doesn't address what the agent asks the sandbox to do — only constrains where it does it.
WasmEdge
github.com/WasmEdge/WasmEdge
Architectural Pattern
WebAssembly runtime with AI extension plugins. Agent tool code compiled to Wasm executes inside a capability-restricted sandbox with explicit limits on memory, CPU time, and permitted syscalls.
Strengths
Sub-millisecond cold start — orders of magnitude faster than microVMs. ~5MB base footprint. Deterministic execution enables reproducible security auditing. Apache 2.0 open-source.
Production Trade-offs
Wasm's capability model is still maturing for general agent tasks. File system and network access require careful capability granting that can inadvertently over-permit. Not all Python tool dependencies compile cleanly to Wasm. Requires pre-compilation of agent tools to Wasm, limiting ad-hoc dynamic tool use.

The Gap Between Walls

Neither layer addresses the semantic boundary — whether a validly-structured tool call, passing LLM guardrails and executing inside a sandbox, represents authorized intent. This is where most production incidents will occur. None of these tools provide unified policy spanning both layers. Until that changes, architecture teams must implement explicit cross-layer validation — logging every sandbox network request back to the LLM guardrail layer for post-hoc audit — rather than assuming either wall is sufficient.

Recommendation: If your agents execute read-only operations — retrieval, classification, summarization — LLM-layer guardrails alone suffice, and runtime sandboxing adds cost without proportional risk reduction. If agents execute code, modify files, or call external APIs, runtime sandboxing is non-negotiable, and LLM-layer guardrails remain necessary to reduce malicious inputs reaching the sandbox. The gap between layers is where your incident response playbook and cross-layer audit logging must live.

Map Your Gap Now

Audit one agent in production: trace a single user request from LLM output through tool execution. Identify which layer — if any — would have stopped a malicious instruction. If the answer is "neither," you have work to do before your agent does.
