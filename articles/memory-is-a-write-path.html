Memory Is a Write Path

Teams build agent memory as retrieval and then wonder why their assistant believes two contradictory things about the same user. Memory is a write path with conflict resolution — design it like one.

LegacyMemory as RAG: embed every message, retrieve the top-k, hope the right version of a fact wins.
ModernMemory as a write path: scoped state, explicit update and invalidation rules, and a time model for facts.

The Real Problem

Most "agent memory" starts the same way: dump the conversation into a vector store and retrieve similar snippets on the next turn. It demos well. Then the user moves cities, changes teams or corrects a preference, and the store now holds both versions. Retrieval returns whichever is semantically closer to the question — which is to say, at random.

The industry frames this as a recall problem and reaches for better embeddings or re-rankers. It is not. Recall is the easy half. The hard half is the write: deciding what is worth storing, whether a new fact updates, contradicts or coexists with an old one, when something stops being true, and who is allowed to change it. Databases solved these questions decades ago with transactions, constraints and temporal tables. Agent memory is relearning them one production incident at a time.

It also matters who is allowed to write. A support agent that stores "customer prefers email" is harmless; a planning agent that writes "the user approved the refund" into shared memory, where a payments agent later reads it, has created an authorization channel nobody designed. Memory written by one agent and trusted by another is an interface, and it deserves the same scrutiny as an API.

This essay maps four real approaches by how they handle the write path, because that is where they actually differ.

What Got Cut

  • Raw context-window stuffing. very long context windows are not memory. Re-sending everything is a cost and latency strategy with no notion of truth, scope or forgetting.
  • Plain vector stores marketed as memory. a store without update semantics cannot resolve a contradiction; it is covered in this site's retrieval reference.
  • Chat-history persistence. saving the transcript is logging. It is necessary, but it is not a model of what the agent knows.
  • Provider-hosted memory features. consumer-assistant memory inside a single chat product is not something you can architect around, test or move.

Inclusion bar: the tool must expose explicit write semantics — update, supersede, scope or delete — that an engineer can reason about and test.

Four Ways to Write a Memory

The approaches below are not competitors on a leaderboard. They sit at different points on one axis: who decides what gets written, and how conflicts are resolved. Most production agents need more than one.

Scoped State & Checkpoints

The first kind of memory is not about facts at all — it is the agent's working state: where it is in a task, what it has already tried, what a human approved. Losing it means redoing work or repeating an action with side effects.

Scoped State & Checkpoints

LangGraph persistence · LangChain

Checkpointers save graph state at every step, scoped to a thread, with Postgres and other backends; a separate long-term store holds namespaced cross-thread memories. Writes are deterministic — your code decides exactly what state is saved — so resume, replay and human-in-the-loop interrupts are reliable.

Limit: it gives you correct storage, not judgement. Deciding which facts deserve long-term memory, and resolving conflicts between them, is still your code.

Extracted Fact Memory

The second approach lets a model read each interaction and extract discrete facts — preferences, entities, decisions — then reconcile them against what is already stored.

Extracted Fact Memory

Mem0 · Mem0

An LLM extraction step proposes candidate memories, and a reconciliation step compares them with similar existing memories and chooses to add, update, delete or ignore. Memories are scoped by user, agent or session. This is the most direct answer to the contradiction problem: the write path explicitly asks "does this change something I already know?"

Limit: reconciliation is itself an LLM decision — it can be wrong, and it costs a model call per write. Log every update and delete so a bad merge can be audited and reversed.

Temporal Knowledge Graphs

The third approach refuses to overwrite at all. Facts become edges in a graph with validity intervals; a contradiction does not delete the old fact, it ends it.

Temporal Knowledge Graphs

Graphiti · Zep

Builds a knowledge graph from episodes with a bi-temporal model — when a fact was true in the world and when the system learned it. New contradicting facts set an invalid_at timestamp on the old edge instead of deleting it, so the agent can answer both "where does she work?" and "where did she work in March?". It is the open-source engine behind Zep's memory service.

Limit: you operate a graph database and an extraction pipeline; ingestion is slower and more expensive than appending vectors, and graph quality depends on entity resolution.

Agent-Managed Memory

The fourth approach hands the write path to the agent itself, treating memory like an operating system treats RAM and disk: a small in-context working set and a larger archive, with the agent deciding what to page in and out.

Agent-Managed Memory

Letta · Letta (formerly MemGPT)

Stateful agents with editable in-context memory blocks and archival memory; the agent calls tools to rewrite its own blocks and search its archive, and all state persists server-side. Fits long-lived assistants whose persona and user model must evolve over months rather than reset every session.

Limit: the model decides what to remember, so memory quality tracks model quality and prompt design; you need evals on memory edits, not just on answers.

Where to Land

Start from the write question, not the retrieval question. Ask: when two memories disagree, who decides, and is the old one deleted, overwritten or ended?

Almost every production agent needs the first layer — scoped, deterministic state for the task in flight — regardless of what else it uses. The other three are choices about long-term knowledge.

Whatever you choose, keep an append-only log of every memory write, update and delete, with the model, prompt and source message that caused it. When a user asks why the assistant believes something — or a regulator asks you to forget it — that log is the only honest answer. It is also the dataset you will need to evaluate whether your write path is improving.

Expect to combine layers. A typical production agent pairs checkpointed task state with one long-term store, and only adds a temporal graph when questions about history become frequent enough to justify running one.

Memory is the one layer of an agent that gets more valuable and more dangerous with every day it runs, so design its write path before it holds anything you cannot afford to lose or leak.

  • Your agent runs multi-step tasks with side effects or human approvals → use checkpointed state (LangGraph persistence or equivalent) first — resumability is a correctness requirement, not a feature.
  • You need per-user preferences and facts that stay current → use extracted fact memory (Mem0) with update and delete logging, scoped by user.
  • Questions involve time — "what did we agree last quarter?", audits, CRM-like histories → use a temporal graph (Graphiti/Zep) so facts are ended, not overwritten.
  • You are building a long-lived assistant whose behaviour should evolve → consider agent-managed memory (Letta), and budget for evals on the memory edits themselves.
  • You only need the last few turns → you do not need a memory layer. Keep the transcript window and move on.

One Move

Pick ten real users or sessions and write down three facts about each that changed over time. Replay those sessions through your memory layer and ask the agent the current value of each fact. If it gets the old value, or both, your problem is the write path — fix it before you touch embeddings.

Bold Reframe

Agent memory doesn't fail on recall — it fails on the write. If your memory layer can't decide which of two facts is current, you've built a contradiction cache.

What's Still Missing (as of Oct 2026)

There is no standard way to evaluate a memory write. Benchmarks test whether an agent can recall a fact, almost never whether it correctly retired an outdated one. Memory also has no portable format: moving a user's memories from one system to another, or honouring a deletion request across all of them, is custom work every time. And access control is thin — few tools let you say that a memory written by one agent may be read but not changed by another. Treat those as your responsibility until the tooling catches up.
